# Changelog

## 1.0.2

A patch release. Pages now carry a Content-Security-Policy, and the font is served by the app instead of fonts.bunny.net, so no browser request leaves your server. Tools, accounts and the database are unchanged: there are no migrations, and the Docker image upgrades with `docker compose pull && docker compose up -d`. If a page ever looks broken after the upgrade, set `CSP_MODE=report-only` (or `off`) and tell us.

- **Companion skill and release notes.** `skills/serveravatar-mcp/SKILL.md` is an optional instruction file for Claude (how to start, what to ask before a change, confirm before a restart even when asked, what the tools cannot do), described in [docs/setup.md](docs/setup.md). Tried through Claude Code with real prompts: it refused a delete plainly, asked for every choice before creating a database or a WordPress site, and held back a restart until it had looked at the server. `.github/release.yml` groups GitHub's generated release notes by pull-request label.
- **CI tokens are read-only.** The `tests`, `lint`, `audit` and `docker` workflows now declare `permissions: contents: read`, which closes four GitHub code-scanning alerts ("Workflow does not contain permissions").
- **Content-Security-Policy.** Pages now send a policy that lets scripts and styles run only when they come from the app itself or carry a one-time nonce made for that request, so an injected `<script>` or `<style>` tag does not run. Fonts, images and connections are limited to the app, plugins are off, and framing stays banned. There is deliberately no `form-action`, so the consent page can still send you back to claude.ai, `http://localhost:PORT` or `cursor://`. To make this work, the Instrument Sans font is now served by the app instead of fonts.bunny.net (no request leaves your server), the page-loading bar's styles moved into the stylesheet, and the nonce is also given to the library that locks scrolling behind dialogs and menus. JSON endpoints (`/mcp`, OAuth) still carry only the framing ban. `CSP_MODE=report-only` makes the browser only log problems and `CSP_MODE=off` removes the page policy. Checked in a browser by clicking through the dashboard, token, connections, activity, users, all-activity and settings pages, plus the user menu and a dialog: no violations. A server-error page (Laravel's plain one) appears unstyled. CI checks the header is sent once with a nonce. See [SECURITY.md](SECURITY.md).
- **Cursor tested.** Cursor connected to a local Docker install over OAuth (it returns to `http://localhost:8787/callback`), listed the tools (25), and `ping` and `list_organizations` ran through it, all visible in the activity log. See [docs/setup.md](docs/setup.md).

## 1.0.1

A patch release. The application behaves as in 1.0.0: this adds a ready-made Docker image, records that Claude Code was tested, and updates CI and docs.

- **Published Docker image.** Each release is now published to `ghcr.io/mayursojitra/serveravatar-mcp` for Intel/AMD and ARM (the image for 1.0.0 was published too), so self-hosters can run it with only `docker-compose.yml` and a `.env` file, no build. Set `SERVERAVATAR_IMAGE` in `.env` to a pinned version (`:1.0.0` or `:1.0`; `latest` can migrate your database on its own) and run `docker compose pull && docker compose up -d`. Pre-releases get only their exact version tag. A new workflow (`release-image.yml`) smoke tests the image before pushing it and again from an empty folder after, and builds both platforms on pull requests that touch the Docker files. The docker CI and the release workflow share one smoke-test script. The Dockerfile's PHP-dependency and front-end stages now always run on the build machine, so the ARM image does not run npm or Composer under emulation. See [docs/self-hosting.md](docs/self-hosting.md).
- **Claude Code tested.** Claude Code connected to a local Docker install over OAuth and listed the tools (25), and `ping`, `list_organizations` and `list_servers` ran through it. It also connected over a public HTTPS tunnel, where `list_servers` worked (reported by the maintainer, not from the activity log). When a call left out a required argument, the tool's error message was enough for the AI to correct it. Cursor is still untested. See [docs/setup.md](docs/setup.md).

## 1.0.0

First stable release of a self-hosted, multi-user MCP server for ServerAvatar.

### Since the release candidates

- **Docker setup steps fixed.** The steps in the first release candidate failed for a new user: `docker compose build` stopped with "APP_KEY is missing", and the documented `key:generate` command printed no key. The key is now generated first with `openssl rand -base64 32`, and the compose and container messages point to it. See [docs/self-hosting.md](docs/self-hosting.md).
- **Each security header is sent once.** The Docker image's nginx added its own `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy` and `Strict-Transport-Security` on top of the app's, so each was sent twice with different values. The image now strips nginx's copies, and CI checks that each header appears once. HSTS now comes from the app only, so behind a proxy `TRUSTED_PROXIES` must be set for the app to see HTTPS. Static files (the built scripts and styles) no longer get nginx's headers.
- **Tests and builds on more setups.** The test suite passes on both MySQL 8 and MariaDB and on Linux as well as macOS, and CI runs it on PHP 8.2 and 8.4. Composer resolves dependencies for the PHP 8.2 minimum.
- **Dependencies.** The one accepted advisory (phpseclib) is gone: Passport 13.12 pulls in a fixed phpseclib, so `composer audit` and `npm audit` both report nothing. Actions and code dependencies were updated.
- **Docs and project files.** Added a code of conduct and a pull request template; corrected the self-hosting guide and the tool counts.

### What it does

- **Accounts.** Login only, no sign-up. Admins exist only because someone ran `php artisan serveravatar:create-admin`; they create normal users, disable them, reset their passwords or delete them. A new or reset user must choose a password before doing anything else.
- **AI clients over OAuth 2.1.** claude.ai (tested end to end), Claude Code and Cursor (instructions written, not yet tested) connect to `/mcp`. Each connection has a permission level the user picks on the consent screen: read only, read plus safe actions, or full. Users can change the level or revoke a connection at any time.
- **One ServerAvatar token per user**, checked with ServerAvatar before it is saved and stored encrypted.
- **24 tools** (and a `ping`): 16 read tools (organizations, servers, server usage and logs, applications, domains, SSL, databases, database users, cron jobs, supervisors, backups, `list_system_users`, and `list_application_types`, which tells the AI which application types it can create and what each needs) and 8 that change things (restart a server, control a supervisor process, create an application, add a domain, install SSL, create a database, change who may connect to a database user, create a cron job). Nothing destructive is offered; `update_database_user` resets that user's password, and says so. It was run live on a test database user. See [docs/tools.md](docs/tools.md).
- **Activity log** of every sign-in, admin action and MCP call, with secrets removed, kept 90 days, with filters and dashboard counters.
- **Docs:** [setup](docs/setup.md), [self-hosting](docs/self-hosting.md) (manual and Docker Compose), [OAuth design](docs/oauth.md), [ServerAvatar API notes](docs/api-notes.md).

### Security work in this release

- A password change or reset now ends what the old password opened. Before, the email reset (and the change in settings) left the user's other browser sessions and every connected AI client working, so recovery after a compromise did not lock the intruder out; only the admin reset did. Now all four flows (email reset, change in settings, forced change, admin reset) delete the user's other sessions, revoke every AI client connection (access tokens, refresh tokens, unused authorization codes) and log how many were disconnected, and `AuthenticateSession` signs out stale sessions with any session driver. The settings page tells the user that their AI clients must be connected again.
- The app answers only to the host in `APP_URL` (plus `TRUSTED_HOSTS` and `localhost`). Before this, a forged `X-Forwarded-Host` header could put an attacker's domain into the OAuth discovery documents and into password-reset links, even with a trusted reverse proxy.
- Every response forbids framing, so the consent page cannot be clickjacked, and sets `nosniff`, `Referrer-Policy` and (over HTTPS) HSTS.
- Dependencies audited: npm and Composer report no known vulnerabilities, and CI re-checks both weekly and on every change. Dependabot proposes minor and patch updates once a month.
- New tests for the host check, the headers, what a token can and cannot do on `/mcp` (disabled account, pending password change, revoked connection, another user's connection, client-credentials), and the supervisor action in the request path.
- A ServerAvatar application record no longer passes along the system user's password.

### Known limits

- One of the eight write tools (control supervisor) follows ServerAvatar's documentation and is tested against a fake, but has not been run on a real server. `create_cronjob` was run live (the job was created, listed and ran as its system user). `add_domain` was run live on a plain PHP application (the domain was added and listed). `install_ssl` was run live (Let's Encrypt, with `force_https` off and on) and the certificate was issued and served, and with it on, HTTP redirected to HTTPS. `create_application` was run live for a plain PHP 8.2 application, for WordPress, phpMyAdmin, Joomla and Statamic (PHP 8.2, nginx) on the user's own domain; the other 9 application types follow the documentation and have not. WordPress needs the admin email, although ServerAvatar's documentation calls it optional. Live `create_application` calls with a ServerAvatar temporary domain got HTTP 500 on two test servers; no application was created and each failed attempt left a system user behind. So the tool no longer uses temporary domains at all: the user's own domain (`hostname`) is required, and that path worked live.
- `create_database` lets the user choose who may connect: the server only (default), specific IPv4 addresses, or everywhere (the AI warns that this exposes the database). All three choices have been run live.
- A live Statamic install outlasted the 20-second request timeout: the application was created but the answer, with the generated passwords, was lost. Creating an application now waits up to 120 seconds (`SERVERAVATAR_SLOW_TIMEOUT`). If the wait still ends, the tool answers `pending` and still returns the generated passwords, and tells the AI to check `list_applications` and not create the application again; any other change that times out says it may have gone through. Akaunting took longer than 90 seconds in a live test. The rerun took about 28 seconds and returned the passwords; the site answered and its control panel login page loaded.
- Application names take letters, digits, hyphens and underscores only, because ServerAvatar rejects spaces (found in a live test).
- `create_application` offers 14 application types, each with its own payload: plain PHP, WordPress, Joomla, phpMyAdmin, Akaunting, Nextcloud, Moodle, PrestaShop, Statamic, Craft CMS, Uptime Kuma, n8n, Node-RED and NodeBB. The AI asks the user to choose (after `list_application_types`, which returns the choice as `type_questions` of at most four options each, so a client with a choice popup can show one; the server cannot open a popup itself, so this is a request to the AI and not guaranteed), and admin passwords and database names are always generated by the server, never supplied by the model. The AI asks for the application's domain, and whether it should run as a new system user (random name and password generated, or the user's own) or an existing one chosen from `list_system_users`. Mautic (needs the user's SMTP password) and the Git-based applications are not offered. Only the plain PHP, WordPress, phpMyAdmin, Joomla and Statamic bodies have been sent to the real API; the rest follow ServerAvatar's documentation.
- Two-factor sign-in, destructive tools, more than one ServerAvatar token per user and MCP resources and prompts are not in this release.
- No independent penetration test. No full Content-Security-Policy for scripts and styles.
- The Docker files (`Dockerfile`, `docker-compose.yml`) have been run by hand (build, health check, sign-in, saving a token), and a CI workflow builds the image and smoke-tests it on every push. There is no published image yet: build it from source.
